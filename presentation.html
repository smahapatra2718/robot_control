Orientation · 01

What the system does

Point a browser at the robot, drag a 3D handle, press play. The arm goes there — in a straight line, under a speed cap, with a stop button that always works.

  • Two arms that share nothing at the transport layer UR15 speaks RTDE — Python commands joints directly. The GoFa has no motion API at all: you write a RAPID program, load it onto the controller, and stream to it over UDP.
  • …converged onto one motion implementation lib/control/ — move_to_joints, move_to_pose, play, set_gripper, stop, estop. Written once, not twice.
  • Four surfaces on top of that one core A viser 3D browser UI · a headless CLI recorder and player · a REST + WebSocket API · a web console with live 3D and camera feeds.
  • Teach by hand, replay by name Hand-guide the arm in free-drive, capture waypoints, save to JSON, replay from any surface.
  • The whole thing runs with no robot attached An offline simulator shims the transports, so the real, unmodified scripts run on a laptop.

Orientation · 03

The two arms are not alike

Python controls the UR directly. The GoFa is a little more complicated.

The four protocols

  • RTDE — Real-Time Data Exchange, Universal Robots. Python reads joint state and writes servoJ targets straight over TCP. Nothing runs on the robot.
  • RAPID — ABB's robot programming language. An ABB arm moves only because a RAPID program tells it to. There is no direct motion API to call.
  • EGM — Externally Guided Motion, a licensed ABB option. It lets a running RAPID program hand control to an external UDP stream. Ours — PyEgm.mod — calls EGMRunJoint and follows the joint targets we send at 100 Hz.
  • RWS — Robot Web Services, ABB's HTTPS API. Not motion: mastership, reading and writing RAPID variables such as egm_go, loading modules, start and stop.

The sys.path bootstrap, and why there's no package

Each script in scripts/ starts by putting the repo root and lib/ on sys.path. That's why you see import robot_common rather than from lib import robot_common, and why scripts work from any working directory.

Asset paths resolve from robot_common._ROOT (the parent of lib/), derived from __file__ — never from the CWD. pyproject.toml sets package = false: there is deliberately no build step and nothing to install.

The repo root is on the path because pyroki_snippets/ — which holds the custom seeded-IK solver — is imported by bare name and is not part of the installed pyroki package.

The lab · 06

The physical setup

None of this is in the repository. The code documents itself; the room does not. This part is the day-one survival guide.

Robots

  • UR15 — Universal Robots, PolyScope X controller. Robotiq Hand-E parallel gripper on the wrist (RS-485 + 24 V through the tool flange).
  • GoFa CRB 15000 — ABB collaborative arm, variant crb15000_5_95 (5 kg payload / 0.95 m reach), OmniCore C30 cabinet with a FlexPendant.

Control PC

  • A Windows machine. All robot code runs inside WSL.
  • Logins for the PC, WSL and the UR pendant are in important_notes.txt on the lab machine — deliberately not in this repository.
  • Two Ethernet connections: one to the robot network, one to the regular network. One of them is a USB-Ethernet dongle.
  • Two USB cameras, one per arm, forwarded from Windows into WSL.
Credentials live outside this repository. github.com/smahapatra2718/robot_control is public, so the Windows / WSL / UR-pendant logins are kept in important_notes.txt on the lab machine, which is gitignored. Ask the lab owner, or read it there. The UR pendant password should never be needed in normal operation.

The one credential that is committed is the GoFa RWS login (Default User / robotics in robot_common.py) — that's ABB's published OmniCore factory default, not a secret. Change it if this cell ever leaves a private network.

The cell

  • The two arms are on two separate tables. Nothing else on them is relevant to operation.
  • The Arducams are monitoring cameras watching the cell — they are not wrist-mounted and nothing in the motion path depends on them.
  • The E-stops are on the pendants, and the pendants live on a separate table.
The two arms can reach each other. Their working envelopes overlap, and nothing in software knows that — there is no collision model spanning the two robots, and a single API server can drive both at once. Two independently valid commands can put them in the same place. Until that changes, the interlock is the operator: move one arm at a time, or check the other's pose first.
Know where the pendant is before you command motion. The E-stops are on the pendants and the pendants are on a different table from the arms — so the stop button is not within arm's reach of the thing you are stopping. Worth a deliberate look before the first move of a session, and worth mentioning to anyone watching a demo.

The confirmed configuration

Captured from the running lab host. This is the part that could not be recovered if the machine were ever reimaged — now it can.

WSL sees both directly — eth4 holds 192.168.125.50 and eth0 holds 192.168.42.176, the same addresses Windows has. That is mirrored networking, and it is the whole configuration:

# C:\Users\sudo\.wslconfig  — two lines, and the reason EGM works at all
[wsl2]
networkingMode=mirrored
Why mirrored is load-bearing, not incidental. Under default NAT, outbound TCP to the robots would still work — RWS and RTDE would look fine. But the GoFa sends EGM feedback inbound to 192.168.125.50:6510, and inbound UDP does not reach a NAT'd WSL (netsh portproxy is TCP-only, so it can't be worked around that way either). Lose this line and the symptom is the nastiest kind: RWS connects, the installer succeeds, egm_go sets true — and the arm never moves. Requires WSL 2.0.0+ on Windows 11 22H2+; this host runs WSL 2.7.10.
The flaky dongle is the robot network. Ethernet 2 — the adapter that carries both arms — is the USB Realtek, the one that needs replugging when the UR15 connect hangs. The built-in 2.5 GbE port carries the ordinary network instead. Worth knowing before you spend twenty minutes debugging RTDE: if both robots go unreachable at once, suspect the dongle first. Swapping the two cables so the robots use the built-in port would remove a whole class of failure.
Security consequence of mirrored mode. WSL shares every Windows interface, and api_server.py binds 0.0.0.0 by default — so the robot API is reachable on the ordinary network at 192.168.42.176:8000, not just the robot subnet. With ROBOT_API_TOKEN unset it would be changeme. Set a real token, or bind --host 127.0.0.1.

A shortcut you can reason out without running anything. Outbound connections to the robots work under either mode — NAT happily carries TCP out through the Windows routing table, which covers RWS and RTDE. But EGM is different: the GoFa sends UDP feedback to 192.168.125.50:6510, and inbound UDP does not reach a NAT'd WSL (netsh portproxy is TCP-only, so it can't be that either). So if the GoFa actually moves under EGM — and it does — the setup is almost certainly mirrored networking. The commands above just confirm it and give you the exact line to record.

Once you have the answers, the durable fix is to commit them: the .wslconfig contents, the adapter name and static IP for the robot network, and any firewall rule. Two or three lines of documentation that make the machine reproducible instead of irreplaceable.

Diagnostics — prove the network before you blame the code 
# GoFa — should reply in well under a millisecond
ping -c 2 192.168.125.1
nc -zv -w 2 192.168.125.1 443          # RWS; OmniCore is HTTPS-only

# UR15 — all four should succeed. Any timeout = PolyScope X firewall.
for p in 29999 30001 30004 63352; do nc -zv -w 2 192.168.125.2 $p; done

If a port times out but ping works, it is almost always the PolyScope X firewall (UR) — see the UR bring-up slide — not a cable.

The routing trap. If the PC is on a VPN that claims 192.168.125.0/24, packets to the robots go into the tunnel instead of out the Ethernet port, and every port appears dead. On Linux/WSL, confirm which interface is chosen:

ip route get 192.168.125.1        # must egress the Ethernet interface, not a tunnel
Flaky link: the USB-Ethernet dongle

Symptom: a script hangs at the UR15 connect stage and never times out cleanly.

Check: look at the link lights on the USB Ethernet dongle.

Fix: unplug and replug the dongle. The link usually comes back immediately. Re-run the script afterwards — a connection that was never established won't recover on its own.

This is a known-flaky adapter, not a code path. If it happens often enough to be disruptive, replacing the dongle with a different chipset is the real fix.

The lab · 08

The control PC: Windows hosting WSL

The code is developed on macOS and deployed into WSL. Those two environments differ in ways that have already bitten — know which one you're in.

  • Everything runs in WSL Log into Windows, open WSL, and work from the repo checkout there. Logins are in important_notes.txt on the machine itself, not in this repo.
  • Windows owns the hardware; WSL borrows it The NICs and the USB cameras are Windows devices. Networking has to reach the robot subnet from inside WSL, and the cameras have to be explicitly forwarded with usbipd.
  • Platform-dependent defaults exist in the code robot_common.py picks a different default second-camera index on Linux than on macOS/Windows, because Linux UVC devices claim two /dev/video* nodes each.
macOS-only setup steps do not apply here. The boost@1.85 dance in the README exists because ur_rtde compiles from source and Homebrew's Boost 1.87+ breaks that build on macOS. On Linux/WSL you need the ordinary build toolchain instead (build-essential, cmake, Boost dev headers) — see the install slide.

The host runs Ubuntu 24.04.1 on WSL 2.7.10 (kernel 6.18.33.2-microsoft-standard-WSL2). The code lives in the robot-control checkout, and uv run from its root launches everything.

The API token is currently left at the default, changeme. Stated plainly because it combines badly with two other facts: mirrored networking shares every Windows interface, and api_server.py binds 0.0.0.0. So while the server is running, anyone on the ordinary 192.168.42.0/24 network can drive both arms — acquire the lease, send a move, engage free-drive.

Fine for a bench nobody else can reach; this bench is reachable. Either fix is one line: 
# pick a real token...
export ROBOT_API_TOKEN='something-long'          # in ~/.bashrc to make it stick

# ...or keep the arms off the network entirely
uv run scripts/real.py api --host 127.0.0.1

Nothing else starts automatically at boot beyond the camera attach — every run is launched by hand.

The lab · 09

Getting the USB cameras into WSL

Two USB cameras, one per arm, forwarded from native Windows into WSL with usbipd-win.

# --- ONE TIME, in an Administrator PowerShell ---
usbipd list                                         # confirm the two cameras are on 2-9 and 2-10
.\scripts\setup_cameras_windows.ps1 -BusId 2-9,2-10  # binds them + registers logon tasks

# --- from then on, nothing. In WSL, just confirm: ---
ls -l /dev/video*
uv run scripts/verify_cameras.py --save   # writes JPEGs so you can tell which arm is which
This used to be a manual step on every boot — it isn't any more. usbipd bind persists across reboots but attach does not, so the cameras had to be handed to WSL by hand each morning. scripts/setup_cameras_windows.ps1 now does the bind once and registers a per-camera logon task running usbipd attach --wsl … --auto-attach, which also survives a replug or a WSL restart. Power on → log in → open WSL → the cameras are already there.
No custom kernel is needed — this is a stock WSL2 kernel. 6.18.33.2-microsoft-standard-WSL2, with uvcvideo loaded as shipped. Older WSL2 kernels genuinely had no UVC support, which is where the "cameras can't work in WSL" folklore comes from; on a current WSL it simply works. If you land on a machine where it doesn't, wsl --update before anything more drastic. (CLAUDE.md asserted the opposite until this was measured — now corrected.)
The cameras are two Arducam 477 12MP-S-HDR on BUSID 2-9 and 2-10, bound with logon tasks registered. Two things follow from them being the same model: they share a USB hardware id (0c40:0433), so the setup script must be given -BusId and not -HardwareId; and only the BUSID distinguishes them, which follows the physical port — move a camera to another socket and the arm mapping swaps. A rebuilt PC needs usbipd list re-run first.
On this machine: /dev/video0 is the UR15, /dev/video2 is the GoFa. Those are exactly the built-in defaults, so no environment variables are needed — leave UR_CAMERA_INDEX and GOFA_CAMERA_INDEX unset and it works.

Note the jump from 0 to 2, not 1: on Linux each UVC camera claims two /dev/video* nodes (capture + metadata) and only the first yields frames, so the second physical camera lands on index 2. That is the reasoning behind _SECOND_CAMERA_DEFAULT in robot_common.py, now confirmed on hardware rather than assumed. If the mapping ever drifts, re-run uv run scripts/verify_cameras.py --save — it writes a JPEG per device so you can just look.
How camera device selection works in the code

UR_CAMERA_INDEX / GOFA_CAMERA_INDEX accept either an integer index or a device path. -1 disables that arm's camera.

UR_CAMERA_INDEX=/dev/video0 GOFA_CAMERA_INDEX=/dev/video2 \
  uv run scripts/real.py api

Prefer a path over an index on Linux, and prefer a stable /dev/v4l/by-id/... symlink over both — indices shift when devices re-enumerate, and one physical UVC camera exposes two /dev/video* nodes (capture + metadata) of which only the first yields frames. That's exactly why the default for the second camera is 2 on Linux but 1 on macOS/Windows.

Cameras are strictly best-effort: a missing camera degrades /camera/* to a 503 carrying the reason, and is printed at server startup. It never blocks serving. camera.py also names the capture backend explicitly (V4L2 on Linux, AVFoundation on macOS) because when no device is present, OpenCV silently falls through to FFMPEG and reports "configure with libavdevice" — which sends you chasing a build flag instead of a missing camera.

The lab · 10

Installing the software

Dependencies are managed with uv. pyproject.toml declares them, uv.lock pins them exactly — including the Python interpreter itself.

git clone <repo> && cd robot_control
git lfs install && git lfs pull     # meshes are LFS — without this the URDFs won't render
uv sync                             # builds .venv/ (~655 MB) from uv.lock

uv run scripts/sim.py ur15          # nothing needs activating; uv re-syncs if the lock changed

Linux / WSL the lab

ur_rtde publishes no wheels, so it compiles from source on every machine. Verified on the lab host (Ubuntu 24.04.1, gcc 13.3, CMake 3.28.3):

sudo apt install -y build-essential cmake libboost-all-dev git git-lfs

That is the whole prerequisite. Ubuntu 24.04 ships Boost 1.83, which is below the 1.87 change that breaks the build on macOS — so on Linux it simply works, no version pinning needed.

macOS dev

Boost 1.87+ made Boost.System header-only, which breaks ur_rtde's find_package. Use the keg-only 1.85:

brew install boost@1.85
export BOOST_ROOT=/opt/homebrew/opt/boost@1.85
export CMAKE_PREFIX_PATH=$BOOST_ROOT
uv sync

The mirror image of Linux: Homebrew ships 1.90, so macOS needs a deliberate downgrade to get below 1.87.

uv owns the interpreter. python-preference = "only-managed" means builds never touch a system or conda Python. This is deliberate: the original hand-built venv was linked against miniconda and broke the moment the repo directory moved. Do not pip install into .venv/ — change pyproject.toml and re-run uv sync, then commit the regenerated uv.lock.
You do not need ffmpeg or the libav*-dev packages. They appear in this host's apt history because they were installed while chasing OpenCV's "configure with libavdevice" message — which is not a build problem at all. cv2 emits it when no camera device is present, having silently fallen through to its FFMPEG backend. The real fix was attaching the camera. camera.py now names the backend explicitly (V4L2 / AVFoundation) so the error points at the missing device instead of a build flag.
Non-obvious entries in the dependency manifest
  • protobuf is a direct dependency. lib/egm_pb2.py imports google.protobuf at runtime and nothing else pulls it in. Drop it and the GoFa EGM path breaks silently.
  • opencv-python-headless, not opencv-python. The server only grabs and JPEG-encodes; it never opens a window, so the GUI build's system libraries are dead weight. camera.py imports it defensively — the repo still runs without it, cameras just report unavailable.
  • xacrodoc is imported nowhere. It regenerates urdf/*.urdf from xacro. The generated URDFs are committed, so it's only needed to rebuild them.
  • jaxls comes from git, not PyPI. pyroki depends on it by URL; uv.lock pins an exact commit, so a cold-cache uv sync needs git and network access.

What PyEgm.mod actually does 
MODULE PyEgm
  PERS bool egm_go  := FALSE;   ! TRUE -> enter EGM joint streaming
  PERS bool lead_go := FALSE;   ! TRUE -> software lead-through (hand-guide)
  VAR egmident egm_id;

  PROC main()
    AccSet 50, 50;
    WHILE TRUE DO
      WaitUntil egm_go = TRUE OR lead_go = TRUE;      ! parked here when idle
      IF lead_go = TRUE THEN
        SetLeadThrough \On;
        WaitUntil lead_go = FALSE;
        SetLeadThrough \Off;
      ELSE
        EGMReset egm_id;  EGMGetId egm_id;
        EGMSetupUC ROB_1, egm_id, "default", "UCdevice" \Joint;
        EGMActJoint egm_id \LpFilter := 20 \MaxSpeedDeviation := 20;
        EGMRunJoint egm_id, EGM_STOP_HOLD \J1 \J2 \J3 \J4 \J5 \J6
          \CondTime := 1 \RampInTime := 0.1 \RampOutTime := 0.2;
        EGMReset egm_id;
        egm_go := FALSE;
      ENDIF
    ENDWHILE
  ENDPROC
ENDMODULE

Python sets egm_go = TRUE over RWS, waits for the first EGM feedback packet, then streams joint targets over UDP. \CondTime := 1 means the instruction returns after one second of convergence — which is why a play holds its final target for HOLD_AFTER_PLAY_S (1.5 s) before letting the session close.

KnobDefaultEffect
\MaxSpeedDeviation20 deg/sController-side per-joint speed cap — a backstop below the Python TCP cap. Raise both together or not at all.
\LpFilter20 HzLow-pass cutoff. Lower = smoother but laggier. This is why the GoFa needs no software jitter filter and the UR does.
\CondTime1 sConvergence time before the session ends. A pause longer than this drops the EGM session — Live mode detects the stale feed and re-arms.

Worth stating plainly because the RobotWare 6 documentation describes it as YuMi-only, and a reasonable person reading ABB's docs would conclude it can't work here. RW7/OmniCore does support it on the GoFa. (If a future controller ever rejects it, the build error surfaces at /rw/rapid/tasks/T_ROB1/program/builderror, and the fallback is teaching in Manual then switching to Auto to replay.)

Operating it · 17

Live follow and free-drive teaching

Live drive robot

The arm chases the gizmo in real time — no plan, no play. The loop reads the gizmo pose, steps the commanded pose a bounded amount straight toward it, solves seeded IK, clamps the joint step, and commands the arm.

  • Snap-on-enable — the gizmo jumps to the current end-effector first, so the arm never lurches toward a stale target.
  • Seeded from the last commanded q, not the measured one — feeding measured joints back into IK produces jitter.
  • Bounded per tick: ≤ LIVE_MAX_LIN linear, ≤ LIVE_MAX_ANG angular, so the tip tracks a line rather than a joint arc.

Free-drive hand-guiding

Hand-guide the arm, capture poses, save them.

  • UR15: teachMode() — zero-gravity hand-guiding. Reliable.
  • GoFa: ticking the box sets lead_go over RWS; the RAPID supervisor calls SetLeadThrough \On and holds the arm compliant. The physical lead-through button still works independently.
  • Capture snapshots live joints + forward-kinematics pose + the current gripper fraction. Add captures the gizmo pose instead.
In simulation, free-drive cannot be hand-guided — there's no physical arm to move, so teachMode is a no-op and "Capture" just re-grabs the current pose. Offline authoring is via the gizmo + Add waypoint, or Live, or Plan. The headless recorder runs fine in sim but every captured point sits at the home pose — a plumbing test, not realistic authoring.
Why the two arms need different follower designs

UR — acceleration-limited follower. The UR has no controller-side smoothing, so the software has to provide it. The follower tracks the IK target through a per-joint profile bounding both speed and acceleration, with desired speed tapered to √(2·a·|err|) so it decelerates to rest without overshoot, plus a one-tick |err|/dt cap that kills dither at rest. This bounds jerk and low-passes IK jitter. It runs at 125 Hz on an exact initPeriod/waitPeriod cadence, because servoJ is jitter-sensitive.

GoFa — simpler, because EGM filters for you. \LpFilter := 20 smooths controller-side, so the Python side only needs a per-tick pose bound and a joint clamp at 30 Hz.

The GoFa re-arm quirk: because \CondTime := 1, a pause longer than a second lets the robot converge and RAPID closes the EGM session. _live_loop detects the stale feed via egm.is_fresh and re-arms on the next motion — expect a brief hitch after a long pause. On exit it holds the last pose so the session closes cleanly.

The remote API

HTTP + WebSocket over the controller. High-level goals only — the network carries commands and telemetry, never the servo loop.

ROBOT_API_TOKEN=secret uv run scripts/real.py api        # both arms, console at /
ROBOT_API_TOKEN=secret uv run scripts/sim.py  api ur15   # one arm, offline
  • The network carries goals — never the servo loop This is the whole point of the server. A remote client posts "move to this pose"; the box cabled to the arm then runs the 8–10 ms control loop locally to get there. The rejected alternative was a socket streaming joint targets from a remote client at 100 Hz, which puts every network hiccup straight into the control cycle. Here a dropped packet delays your next command — a motion already running is untouched.
  • Bearer token on every endpoint ROBOT_API_TOKEN, defaulting to changeme with a startup warning. Set it for anything beyond a direct cable.
  • A single-writer lease POST /control/acquire returns a lease_token that every write must carry in an X-Lease header. A second client gets 409 — or can {"force": true} to steal it, which stops the current motion first.
  • Commands are asynchronous Writes validate, submit, and return 202 {command_id}. Poll GET /command/{id} or watch the telemetry stream for completion.
  • Stop and E-stop need no lease Any authenticated client can always stop the arm. That path is deliberately never gated on holding the lease.
  • An open telemetry WebSocket is the deadman If the lease holder goes silent while the arm is live, a watchdog stops it and releases the lease.
Why that boundary is what makes remote control safe

Every other safety property on this slide follows from it. Because the arm only ever receives goals, the worst a badly-behaved or disconnected client can do is fail to send the next one. It cannot produce a jerky motion, and it cannot leave the arm mid-trajectory with no one driving it — the motion in flight completes under local control regardless.

That is also why the deadman is a watchdog on the telemetry socket rather than something in the motion path. The question it answers is not "did a packet arrive on time" (nothing depends on that) but "is the operator still there at all". If the lease holder goes silent while the arm is live, the watchdog stops it — a policy decision layered on top, not a real-time requirement.

And it is why speed is validated to (0, 1.0] and joint vectors are shape- and finiteness-checked at the edge: since the client's influence is limited to the content of a goal, validating that content is sufficient. There is no second channel through which a client could affect the arm.

  • The command executor — one motion at a time; submitting while busy raises Busy; stop/estop preempt.
  • The state-poll thread producing RobotState.
  • Segment building and interpolation — Cartesian and joint-space.
  • A bounded command history, so /command/{id} still answers after completion.

Subclasses own per arm

  • _connect / _close
  • _read_q · _read_safety
  • _fk_pose · _ik
  • _run_play — the servo stream (servoJ vs EGM)
  • _graceful_stop

The motion loops were lifted from the tuned teleop scripts, not rewritten — so behaviour matches what those scripts already did. Each subclass also adds its own extras: the GoFa carries four methods with no UR counterpart (_set_go, _start_egm and the two TCP-speed caps), all EGM-session machinery that has no reason to exist in the base.

A third arm is eight methods. The base declares exactly eight hooks as NotImplementedError — _connect, _close, _read_q, _read_safety, _fk_pose, _ik, _run_play, _graceful_stop. Implement those and the new arm inherits the API, the web console, the trajectory format, the offline sim, the lease and deadman, and every speed cap without further work. That is the clearest measure of what the abstraction actually bought.

How it works · 24

The motion model

Two interpolation modes, one velocity profile, and a hard speed ceiling that the user interface cannot raise.

Cartesian move_to_pose · play

The tip travels a straight line. Each tick lerps position and slerps orientation between the segment's two poses, then re-solves seeded IK. Endpoints are anchored to the exact joint goals so the ends are never approximate.

Joint-space move_to_joints

A joint command should move in joint space. A straight Cartesian line between two arbitrary joint configurations can be unreachable or cross a singularity — so this one deliberately does not try.

The trapezoidal profile

Every segment advances alpha ∈ [0,1] linearly in time, then maps it through alpha_to_s() — parabolic acceleration, linear cruise, parabolic deceleration, with zero velocity at both ends. RAMP_FRAC = 0.25 by default; 0.5 gives a pure triangle, 0.1 a sharper ramp.

speed │ ┌─────────────────┐ │ ╱ ╲ RAMP_FRAC = 0.25 │ ╱ ╲ │ ╱ ╲ └────┴───────────────────────┴────► alpha 0 .25 .75 1
The GoFa speed cap is computed analytically, not by simulation. For a straight tool line the peak speed is exactly ‖p₁−p₀‖ · v_peak / seg_duration, so _cap_seg_duration_cartesian() stretches each segment until real TCP speed is under MAX_TCP_SPEED (0.25 m/s, the ISO/TS 15066 collaborative limit). The slider can only scale below that cap — no combination of slider and pose can exceed it.

How it works · 25

Why the stock IK solver wasn't enough

PyRoki's example solve_ik has no seed and no posture cost. It returns a valid solution — frequently in a distant null-space branch.

  • The failure looks like a bug but isn't You ask for a pose 5 cm away and the wrist flips 180° or the elbow swings to the other side. The solution is correct; it's just not the one a human meant.
  • Two additions fix it pk.costs.rest_cost(joint_var, q_seed, weight=rest_weight) pulls the solution toward the seed, and initial_vals starts the optimizer at the seed rather than at zeros.
  • The trade-off is ~0.5 mm of pose error at rest_weight = 2.0 Raise it to 5–10 if branches still flip; the target drifts more but stays in the same kinematic family. That's almost always the better deal for teleoperation.
First call costs ~800 ms — JAX JIT compilation. Subsequent calls are milliseconds. Both teleop scripts call _warmup_ik() at launch (a no-op solve at the current pose) so that cost lands during startup instead of on your first Plan click. The headless scripts import jax lazily for the same reason, which is also why forward kinematics is deliberately not shared in robot_common.py.

How it works · 26

The offline simulator

It doesn't reimplement the robot. It runs the real scripts and lies to them about what's on the other end of the socket.

sim.py ur15 │ ├─ robot_sim.install() inject fakes into sys.modules: │ rtde_control, rtde_receive, │ hande_gripper, abb_rws, abb_egm │ └─ runpy → scripts/teleop_ur15.py ← the REAL script, unmodified │ └─ import rtde_control ← gets the fake, transparently
  • Every feature works in simulation automatically Because it literally executes teleop_ur15.py. There is no second implementation to drift out of sync.
  • The fakes sit at the transport layer Perfect-tracking kinematics, plus a fake RAPID supervisor that mimics the egm_go handshake. The IK, the profiles, the UI and the URDFs are all real.
  • "Offline" means no robot, not no dependencies It still needs the .venv — it runs the genuine jax/pyroki/viser stack.
  • This is what made the big refactors safe Lifting motion logic out of two large teleop scripts into a shared controller is terrifying without a way to test it. The simulator arrived two days before that refactor — not a coincidence.
The one honest limitation: free-drive can't be hand-guided in simulation. There's no arm to move, so teachMode is a no-op and captured points sit at the home pose. Offline authoring goes through the gizmo, Live, or Plan. Home poses are tunable constants in lib/robot_sim.py.

  • Stop is never lease-gated Any authenticated client can stop the arm at any time, including one that never held the lease. Requiring a lease to stop a robot is exactly backwards.
  • A compliant arm never outlives its lease Stop, E-stop, a forced steal, the deadman, and lease release all end free-drive. The arm cannot be left hand-guidable by a client that has gone away.
How the deadman actually works

An open, lease-matched telemetry WebSocket is the heartbeat — there's no separate ping endpoint to forget. If the lease holder goes silent while the arm is live (a motion running, or free-drive engaged), the watchdog stops the arm and releases the lease.

Two documented traps, both in docs/robot-state-reference.md:

  • Polling GET /command/{id} does not keep the deadman happy. Only the WebSocket does.
  • active_command.progress is per segment, and reports an interrupted segment as finished. Don't treat it as overall completion.

RobotState — the one shape

Produced by the controller's poll thread, consumed by every surface. If you learn one data structure in this codebase, learn this one.

{
  "ts": 1215836.808,          // monotonic — pairs with camera frame timestamps
  "robot": "ur15",
  "q": [0.1, -1.4, 1.2, -1.3, -1.5, 0.0],       // six joints, radians
  "pose": {"pos": [x,y,z], "wxyz": [w,x,y,z]},  // grasp / end-effector pose
  "gripper_frac": 0.0,        // 0 open .. 1 closed; null if no gripper
  "safety_state": "NORMAL",
  "controller_state": "RUNNING",
  "activity": "idle",         // idle | moving | playing | stopped | freedrive
  "active_command": {"id": null, "kind": null, "status": null,
                     "progress": null, "error": null},
  "conn_ok": true,
  "health": { … }             // transport-specific extras
}
  • active_command is never null Its sub-keys are always present, so a client can read active_command.status without null-checking the parent, and the served shape never changes underneath it.
  • ?flat=1 gives a scalar-only version q_0…q_5, pose_pos_x, command_status — for clients that can't walk nested JSON. Identical key set on every frame and for both arms.
  • Absent values are None, never a missing key A consumer never has to distinguish "not applicable" from "field disappeared".

War stories · 29

Chasing the last millimetre

Nine commits over two days, all on one problem: the arm stopped near the end of a trajectory instead of at it.

Symptom
A play would finish and the arm would sit visibly short of the taught pose — and then snap back slightly when the next command arrived.
Cause 1 — the stream ended before the arm arrived
servoJ is a target, not a guarantee. When the loop stopped sending, the arm stopped wherever it had got to. Fix: hold the final target until it actually converges.
Cause 2 — "good enough" was a moving target
A fixed tolerance was either too loose (visible error) or unreachable (hung forever). Fix: plateau detection — keep holding while error still improves by at least UR_SETTLE_EPS_RAD; after UR_SETTLE_STALL_TICKS non-improving checks you are at the hardware floor, so stop. Capped at UR_SETTLE_MAX_S so it can never hang.
Cause 3 — gravity droop from an undeclared payload
The ~1 kg gripper made servoJ hold the loaded joints slightly below target. Fix: setPayload(1.0, (0,0,0.06)) at startup so the controller compensates.
A red herring worth knowing
The error looked worse than it was. The gizmo targets the grasp point, ~156 mm past tool0, so the same joint error shows up as a larger Cartesian shift. Geometric, not a regression.
Result: a stiffer settle gain (600 vs 300 during motion) plus plateau detection drives joint error to the servoJ floor — roughly 0.6 mm at the tip — on every play, regardless of load. The transferable lesson: when you can't pick a tolerance, stop guessing and detect when improvement stops.

War stories · 30

The gripper that couldn't be talked to

A design constraint that only appears once both halves are running at the same time.

  • The conflict ur_rtde keeps its control script resident for the whole session. A Robotiq gripper program also needs to run on the controller. Both cannot hold the program slot, so the obvious approach — run the vendor's gripper program — is structurally impossible.
  • The insight The Grippers URCap doesn't only provide a program. It also runs a background daemon that owns the wrist RS-485 bus and serves a socket on port 63352 — independent of whatever program is running.
  • The result hande_gripper.py speaks that socket's newline-terminated ASCII protocol, stdlib only. It coexists with ur_rtde, and the pendant's own gripper buttons keep working because they talk to the same daemon.
# the whole protocol, essentially
SET POS 255 SPE 255 FOR 150 GTO 1   →  ack        # 0 open .. 255 closed
GET STA                             →  STA 3      # 3 = activated
GET OBJ                             →  OBJ 2      # 1/2 = stopped on an object
Port 63352 is firewalled by default in PolyScope X, exactly like RTDE. Open it under Settings → Security → Services, and run scripts/verify_hande.py before trusting gripper control. If it stays unreachable, the fallbacks are a USB-RS485 adapter speaking Modbus directly, or the RS485 URCap socket bridge — both absorbed by swapping the transport inside HandEGripper. The connection is best-effort: with no socket, the system logs it and runs visualisation-only.
One tracked value. gripper_frac (0.0 open … 1.0 closed) is the single source of truth — the slider drives it, waypoints record it, the render always shows it, and the startup "open" command means the value is known without polling. Legacy "open"/"close" strings in old trajectory files normalise on load.

War stories · 32

A machine cabled to a robot has no internet

An obvious statement that quietly invalidates a lot of standard tooling. Several decisions in this repo exist only because of it.

  • Swagger UI is vendored FastAPI's stock docs page loads swagger-ui-bundle.js from a CDN. On the robot network that's ERR_NAME_NOT_RESOLVED and a blank page. Both apps are built with docs_url=None and re-add /docs pointed at web/vendor/swagger-ui/. ReDoc was dropped — CDN-only, same failure.
  • The 3D viewer uses a native import map, no bundler and no CDN three.js and urdf-loader are vendored as ESM. Model bundles are baked and committed so the server doesn't need a robot_descriptions cache to serve them.
  • The console is a single static file Served same-origin, so there's no CORS and the token never leaves the tab. No build step means nothing to rebuild on a machine with no npm registry.
  • uv.lock pins everything, including the interpreter Reproducibility on a machine you can't casually reinstall.
The general principle: assume the deployment machine has no DNS, no package registry, and no second chance. Anything that fetches at runtime is a latent outage. Everything this system needs to render or serve is in the repository.
Other gotchas worth carrying forward
  • Boost 1.90 breaks ur_rtde on macOS. Boost made Boost.System header-only in 1.87+, so no boost_system-*-Config.cmake ships and find_package(boost_system CONFIG) dies. This bites on every machine because ur_rtde publishes no wheels and always compiles. Fix: keg-only boost@1.85 plus BOOST_ROOT/CMAKE_PREFIX_PATH.
  • yourdfpy can't open file:// URIs. xacrodoc resolves package:// into absolute file:// paths, but yourdfpy's filename_handler only fires for unresolved URIs — so the path goes straight to trimesh, which fails. Both local URDFs are generated with the file:// prefix stripped back to package://.
  • The GoFa variant matters. An early commit fixes crb15000_12_127 → crb15000_5_95. Match the URDF to the hardware nameplate — wrong link lengths mean wrong IK, silently.
  • The pre-uv venv broke when the repo directory moved — it was linked against a miniconda interpreter. That's the direct reason uv now manages the interpreter too.

Operations · 33

E-stop and recovery

The most important operational procedure in the system, and the one most likely to be needed while someone is watching.

The rule, from your notes: after any E-stop or safety stop, you must restart the script and restart the robot-side processes. Recovering the robot alone is not enough — the Python side is holding a transport session that no longer corresponds to reality.

Why a restart is genuinely required

  • UR15: a protective stop tears down the control session. ur_rtde's resident control script is gone, so every subsequent servoJ goes nowhere.
  • GoFa: the safety stop halts the RAPID program. PyEgm is no longer parked at its WaitUntil, so setting egm_go has no effect and the arm silently ignores a perfectly valid UDP stream. It must be brought back to Main and started.

UR15 recovery verified

  1. Clear the cause (release the E-stop, remove the obstruction).
  2. On the pendant: acknowledge the fault and re-enable the robot; confirm the ring is green.
  3. Confirm Remote Control mode is still selected.
  4. Ctrl-C the Python process and restart it.

GoFa recovery verified

  1. Clear the cause; release the E-stop.
  2. Pendant: motors on.
  3. Pendant: PP to Main, then green Play — PyEgm must be running and parked again.
  4. Ctrl-C the Python process and restart it.
  5. If RWS now refuses mastership, wait ~30 s for the orphaned session to time out.
Confirmed procedure. Both sequences above are verified against the real cell. The two steps people skip are re-checking Remote Control mode on the UR after a protective stop, and remembering that on the GoFa PP to Main + Play is not optional — without it the arm accepts the EGM stream and silently ignores it.
The software stop paths (distinct from a physical E-stop)

POST /estop is visible in safety_state, so a client can tell an emergency-stopped arm from a merely idle one. Neither software path is a substitute for the physical button — they're for "stop this motion now", not "someone is in danger".

The GoFa hard stop halts RAPID and drops lead-through, but does not do a software motors-off over RWS. Recovery is PP-to-Main + Play, or re-running the installer.
